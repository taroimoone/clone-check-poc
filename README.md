# C#のクローンと修正の反映漏れを自動検出する

mainから分かれたブランチ1でAをBへコピーし、別担当者のブランチ2がAの修正を先にmainへ取り込むケースを検出します。A・Bのペア、ファイル名、ディレクトリの対応表の登録は不要です。

## ローカルで再現する

Python 3.11以上とGit 2.38以上が必要です。以下はPowerShellの例です。LinuxやWSLでは `py -3` を `python3` に読み替えてください。

```powershell
py -3 -m pip install -r ci/requirements-clone-check.txt
py -3 -X utf8 demo/reproduce.py
```

デモは一時ディレクトリにGitリポジトリを作り、次の7ケースを検証します。

| ケース | 結果 |
| --- | --- |
| Aだけを修正したブランチ2が先にmainへ入った。離れたディレクトリのBはメソッド名・引数名を変更済み | 反映漏れ候補 |
| Aの修正がmainへ入る前 | 指摘なし |
| Bにも修正を適用済み | 指摘なし |
| Bに独自変更があり、似た別メソッドも候補に残る | 要確認 |
| 既存ファイルにBのメソッドを追加 | 反映漏れ候補 |
| rebase済みで、分岐時点を `--base` で指定 | 反映漏れ候補 |
| Bを追加しないブランチ2 | 指摘なし |

変更と無関係なC#ファイルを5,000個置いた合成リポジトリでの中央値です。Linux x86_64、Python 3.12.14、Git 2.56.1で各10回実行。Python起動、Git差分、候補の自動探索、仮マージを含みます。サンプル生成、ライブラリのインストール、ネットワーク通信、GitLabランナー起動は計測外です。変更ファイルは各ブランチ2件で、メソッド数を変えています。

| 追加したBのメソッド数 | 自動検出と判定 |
| ---: | ---: |
| 1 | 71.6 ms |
| 100 | 109.2 ms |
| 1,000 | 399.5 ms |

## 実リポジトリで試す

解凍した `ci/` をリポジトリのルートへ配置します。

```powershell
git fetch origin
py -3 -X utf8 ci/clone_check.py --target origin/main --head origin/branch1 --stats
```

判定の手順は次のとおりです。

1. 共通祖先からmainまでの差分で変更されたC#ファイルを集め、同じファイル・型・シグネチャで本体が変わったメソッドを特定します。それぞれの旧版をコピー元候補にします。
2. 共通祖先からブランチ1までの差分で追加・変更されたC#ファイルから、新しく現れたメソッド本体を抽出します。既存ファイル内に追加されたメソッドも対象です。
3. コメントとトークン間の空白を除き、引数名を引数の位置でそろえて照合します。メソッド名やディレクトリの近さは条件に使いません。文字列リテラルは原文を保ちます。16トークン以上の本体を比較し、近似候補には24トークン以上、共通の5トークン断片、トークン列の類似度0.88以上を要求します。定型コードに偏った検索を避けるため、広く共通する断片を除外し、近似比較を最大32件に絞ります。
4. 候補が見つかったら仮マージします。仮マージ後のAがmainの新版と同じで、Bが旧Aと一致し、候補が一意なら「反映漏れ候補」です。似たものが複数残る場合や、本体に独自変更がある場合は「要確認」と表示します。同じ修正内容の本体と一致する場合は指摘を出しません。

この版はC#のメソッド本体を対象にしたPoCです。既存メソッドの一部分をコピーしたケース、短い共通処理、ファイル移動やシグネチャ変更を伴うコピー元の更新、振る舞いが同じ書き換えの判定には対応範囲の制約があります。mainをブランチ1へ取り込んだ後やrebase済みの場合は現在の共通祖先が進むため、ローカルでは `--base <元の共通祖先>` で比較範囲を戻せます。付属CIでは現在の共通祖先を使います。

## GitLabに移す

1. ローカルで使った `ci/` をコミットし、付属の `.gitlab-ci.yml` の `clone_check` ジョブをプロジェクトの設定に追加します。既存の `workflow: rules` がある場合はMRパイプラインの実行を許可します。サンプルのDocker系ランナーは依存ライブラリをpipで取得します。社内パッケージミラーや依存を組み込んだランナーイメージにも差し替えられます。
2. MRを開くと取り込み先の最新コミットをfetchし、同じスクリプトで判定します。結果はジョブログと `clone-check.md` に出ます。追加pushでも動きます。MRを先に開いてからmainだけが進んだ場合はMRパイプラインを再実行します。
3. コメントまで試す場合は、アクセスを制限した検証用プロジェクトでBot用の書き込み可能なトークンを `MR_CLONE_COMMENT_TOKEN` に設定します。Botのコメントを1件にまとめ、追加push後は同じコメントを更新します。トークン未設定でも検査できます。

CI定義とスクリプトはソースブランチに含まれます。本番で広く使う場合は、投稿トークンを参照する処理を信頼済みのジョブやBotに置いてください。MRパイプラインと保護変数で利用できる条件はGitLabの設定に依存します。
